# System coverage, reports and release evidence

These read-only validators evaluate supplied evidence against declared obligations. They do not execute tests, authenticate a source, publish a package or confer regulatory approval. `PASS` always describes the stated evidence contract. Empirical model performance remains a separate assessment.

## Explicit system coverage

`validate_system_coverage(cells, function_inventory, journeys, evidence, scope=...)` requires five named axes: `customer_segment`, `product`, `lifecycle`, `method`, `granularity`. The scope carries a `scope_id`, `version`, `reference`, allowed axis values and nonempty `required_cell_ids`. It does not invent obligations from the Cartesian product. Each declared axis value must nevertheless occur in an explicit cell, so an omitted customer segment or account-month granularity remains visible.

Each cell has a unique `cell_id`, the five `axes` coordinates and `applicability`: `REQUIRED`, `NOT_APPLICABLE` or `GAP`. A required scope obligation cannot be downgraded. Non-applicability requires a versioned decision with `reason`, `authority`, `reference` and `reason_code`: `OUTSIDE_BUSINESS_SCOPE`, `INCOMPATIBLE_TARGET` or `INAPPLICABLE_LIFECYCLE`. Lack of implementation is not a valid reason. Duplicate coordinates and uncovered levels block completion.

Required cells carry `contracts` with nonempty references for `data`, `target`, `result`, `measure`, `horizon`, `model_profile`, `policy_profile`, plus `function_ids`, `journey_ids`, `evidence_ids`. Inventory functions must be `IMPLEMENTED` with both `python` and `r` in `languages`. Each linked journey's `function_ids` must cover the declared cell functions. Evidence records contain unique `evidence_id`, matching `cell_id`, `kind`, `language`, `status`, `reference`, `content_hash`. Require PASS evidence separately in Python and R for `data_target_contract`, `independent_oracle`, `positive_routing`, `negative_routing`, `decision_trace`, `monitoring`, `source_review`; require `parity` with language `both`. Evidence links cannot be borrowed from another cell. These are evidence checks, not a percentage-based waiver of missing obligations.

## Validation report

`validation_report(results, acceptance_policy=..., manifests=...)` bundles full `ValidationResult` payloads and applies explicit separate acceptance criteria. Result records carry `result_id`, `result`, `reference`, `data_origin` (SYNTHETIC, EMPIRICAL, SOFTWARE or MIXED) and `manifest_hashes`. The latter bind each result to the canonical hashes of the supplied `model_manifest`, `data_manifest`, `split_manifest`; each manifest maps artifact names to lowercase SHA-256 strings. The manifests also declare `evaluation_started_at`.

The acceptance policy declares `policy_id`, `version`, `reference`, `declared_at`, nonempty `required_result_ids`, and `criteria`; declaration must precede evaluation. Each criterion has a unique `criterion_id`, `result_id`, ordered object-key `path`, `operator` (LE, GE, EQ, BETWEEN), `threshold` and `rationale`. BETWEEN requires two ordered finite bounds; EQ permits finite numeric, Boolean or string scalars without type coercion. Required results need an explicit criterion; a criterion can test `decision/status == PASS` for a contract audit. Undefined/nonfinite/missing metrics are non-estimable. A failed, blocked or non-applicable required result remains blocking even when another scalar criterion passes. P-values are never averaged or combined. Results, observed criteria, references, content hashes and open issues remain available for a human-readable rendering; synthetic evidence is tagged separately.

## Exact candidate assessment

`release_candidate_assessment(candidate, evidence, requirements=...)` consumes evidence about actual external test runs. Unit-test fixtures that exercise this assessor are illustrative evidence, never claims about a real candidate.

A candidate declares `candidate_id`, `artifact_hashes` including `python_wheel`, `python_sdist`, `native_r`, and `resource_hashes`. All digests are lowercase SHA-256. Requirements contain `requirements_id`, `version`, `reference`, nonempty `required_cell_ids` and `required_journey_ids`, explicit `required_generator_ids` and `required_profile_ids` (possibly empty if none promised), exact expected `resource_hashes`, and positive limits `max_runtime_seconds`, `max_peak_memory_mb`. Scope completeness is the responsibility of the frozen requirements and system-coverage evidence; the assessor cannot discover an undeclared promise.

Each evidence record carries `evidence_id`, `scope_type`, `scope_id`, `kind`, `language`, `status`, `reference`, `content_hash`, `data_origin`, `candidate_id`, `artifact_hashes`, `resource_hashes`. Every record must bind to the entire exact candidate/resource manifest. Wrong-candidate evidence blocks the assessment and cannot satisfy a gate. Duplicate observations for a gate are not cherry-picked: every matching record must pass.

CELL gates require the same evidence kinds and languages as system coverage. JOURNEY, GENERATOR and PROFILE gates require `kind='installed_execution'` separately for languages/runtimes `python_wheel`, `python_sdist`, `native_r`. PACKAGE gates also require each runtime, with its runtime name as `scope_id`. Every installed-execution record requires actual `executed=True`, `installed=True`, `offline=True`, `source_tree_access=False`, finite nonnegative `runtime_seconds` and `peak_memory_mb` within declared limits. A source-tree R run, skipped generator, old wheel, missing measurement or unresolved mandatory gate blocks completion.

Software/system acceptance, presence of synthetic method evidence, empirical performance and regulatory approval are separate output axes. This assessor sets the latter two to NOT_ASSESSED. PASS means the supplied exact-candidate evidence satisfies the declared obligations; it is not independently authenticated execution or permission to publish.
