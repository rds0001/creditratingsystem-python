# Source lineage and historical replay validation

## Source lineage

`validate_source_lineage(nodes, edges, joins, reconciliations, uses, contract=...)` checks actual supplied row identities, dated dependencies and join allocations. It does not authenticate an upstream file merely because its hash was supplied.

The contract declares `contract_id`, `version`, `reference`, `amount_fields` (field-to-currency map), nonnegative `absolute_tolerance` and `relative_tolerance`, `required_node_ids`, `required_use_ids`, and explicit `required_join_ids` (possibly empty). Comparisons use absolute tolerance plus relative tolerance times the expected magnitude. Material amounts remain separate by field/currency; no cross-currency summation is performed.

Nodes have unique `node_id`, `kind` (SOURCE, TRANSFORM, FEATURE, TARGET, PREDICTION, DECISION), `schema_version`, `vintage`, `revision`, `transformation_version`, `content_hash`, `observed_at`, `available_at`, and `records`. SOURCE nodes also declare `source_id` and `semantic_role` (FEATURE, OUTCOME, POST_DECISION). Each record has unique `record_id`, nonnegative `weight`, and finite signed `amounts` for exactly the contracted fields. Joined input records additionally carry `join_key`. Node hashes identify declared upstream snapshots; node totals are independently calculated from the actual records supplied here.

Edges contain `parent_id`, `child_id`. The dependency graph must be acyclic. Sources must be roots, derived nodes require parents, and no child may be produced before its input became available. Reconciliations contain `reconciliation_id`, `node_id`, `reference`, `expected_record_ids`, `expected_total_weight`, `expected_amounts`. These independent expected figures are compared with actual identities, weights and amounts. Every required node must have a reconciliation.

Joins declare `join_id`, left/right/output node IDs, `cardinality` (one_to_one, one_to_many, many_to_one, many_to_many), `join_type` (inner or left), `weight_contract='LEFT_WEIGHT_ALLOCATION'`, `amount_origin='LEFT'`, `mapping`, `excluded_left_ids`, `unmatched_right_ids`. Mapping rows contain unique `output_id`, `left_id`, nullable `right_id`, and nonnegative `allocation_weight`. Input business-key multiplicities must satisfy the declared cardinality; all matching equality-join pairs must be present, each once. Both inputs must directly parent the output. Unmatched outputs are permitted only for genuinely unmatched left rows of a left join. Exclusion lists and output identities reconcile exactly to the actual ledger.

For each retained left record, allocation fractions must sum to one. Each output weight and left-origin amount must equal its input quantity times the fraction. Thus one 100-EUR record joined to two matching right records can produce two 50-EUR allocations, but not two full 100-EUR exposures. This is an explicit conservative allocation convention, not a general SQL join implementation; other economic amount-origin contracts should be reconciled upstream into appropriate nodes.

Uses declare `use_id`, `node_id`, `purpose` (FEATURE, TARGET, PREDICTION, DECISION), `as_of`, `known_at`, `source_snapshot_hashes` keyed by SOURCE node ID. Every ancestor must be available by the historical knowledge cutoff, and the binding must include exactly the source snapshots reached through the DAG. Predictive uses cannot include future observations, TARGET ancestors or OUTCOME/POST_DECISION sources. TARGET uses may legitimately include later outcome observations, but still respect their stated knowledge cutoff. Late revisions remain new snapshots; a matching business date does not make them historically available.

## Historical replay

`replay_consistency(event_log, original_checkpoints, replayed_checkpoints, snapshot_manifest=..., replay_contract=...)` compares actual supplied outputs of an operational replay with frozen original checkpoints. It does not execute a substitute event engine or overwrite an original decision.

The replay contract declares `contract_id`, `version`, `reference`, nonempty `required_checkpoint_ids`, nonnegative absolute/relative tolerances, `ordering='KNOWN_AT_SEQUENCE_EVENT_ID'`, `idempotency='FIRST_IDENTICAL_DELIVERY'`, `corrections='APPEND_REVISION'`. State tolerance uses the original numeric magnitude; types, object keys and array ordering otherwise remain exact. JSON arrays must be explicit lists in native R when scalar/array distinctions matter.

Each event contains `event_id`, `idempotency_key`, `occurred_at`, `known_at`, nonnegative integer `sequence`, object `payload`, its canonical `payload_hash`, and nullable `revision_of`. Occurrence precedes knowledge. Identical repeated deliveries are counted and applied once; the same event or idempotency key with different immutable content is rejected. Revisions append after an existing earlier ordered event. The delivery-log hash includes repeated deliveries; the expected applied sequence is the unique log sorted by knowledge date, sequence and event ID, filtered to events occurring by the checkpoint as-of and known by its knowledge cutoff. A late-known correction cannot change an earlier checkpoint.

Snapshot records contain unique `snapshot_id`, `kind` (MODEL, CALIBRATION, POLICY, SOURCE), lowercase SHA-256 `content_hash`, `known_at`, `effective_from` and nullable exclusive `effective_until`. Each original checkpoint must bind all four kinds with `snapshot_hashes` keyed by snapshot ID. Snapshots must be historically available and effective at that checkpoint.

Original and replay records contain `checkpoint_id`, `as_of`, `known_at`, exact `event_log_hash`, `snapshot_hashes`, ordered `applied_event_ids`, object `state`. Replays additionally require `mode='REPLAY'`. Both sequences are checked against the log, so an already-corrupt original event list is not accepted merely because the replay copied it. Changed cutoffs, changed snapshots, missing checkpoints, repeated/omitted/out-of-order applied events and material state differences are explicit blocking findings. A new model or policy is a counterfactual recomputation, not historical replay. State hashes, numeric differences, differing paths and eligible revision counts remain visible.

A minimal oracle has a 100 balance event delivered twice and a correction to 80 known two days later. The first checkpoint applies the original once and retains 100; the later checkpoint applies original plus correction and retains 80. The assessor verifies these supplied actual states and event bindings; it does not infer that every possible operational engine is correct.
